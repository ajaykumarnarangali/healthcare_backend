Mocking Certificate Authority (CA)
We are creating our own CA for mTLS-based service-to-service authentication in our healthcare microservices.

1. Generate CA private key
openssl genrsa -out ca.key 4096


Explanation:
- openssl – Cryptographic toolkit.
- genrsa – Generates an RSA private key.
- -out ca.key – Saves the generated private key as ca.key.
- 4096 – RSA key size in bits.
Purpose: This private key is used by the CA to digitally sign certificates for individual microservices. It must remain secret.

2. Generate CA certificate
openssl req -x509 -new -key ca.key -sha256 -days 365 -out ca.crt -subj "/CN=Healthcare-Development-CA"


Explanation:
- req – Handles certificate requests and certificate generation.
- -x509 – Generates a self-signed X.509 certificate.
- -new – Creates a new certificate.
- -key ca.key – Uses the CA private key.
- -sha256 – Uses SHA-256 for the certificate signature.
- -days 365 – Certificate validity period of 365 days.
- -out ca.crt – Saves the certificate as ca.crt.
- -subj "/CN=Healthcare-Development-CA" – Sets the certificate's Common Name (CN).
Purpose: Creates the CA's self-signed public certificate. Individual services will use this certificate to verify certificates issued by our CA.

Final output:
ca/
├── ca.key   # CA private key (signs certificates)
└── ca.crt   # CA public certificate (used for verification)


Overall: ca.key signs service certificates, while ca.crt allows other services to verify that those certificates were signed by our trusted CA.

3. Generate Auth Service private key
openssl genrsa -out server.key 2048


Explanation:
- openssl – Cryptographic toolkit.
- genrsa – Generates an RSA private key.
- -out server.key – Saves the private key as server.key.
- 2048 – RSA key size in bits.
Purpose: Generates the Auth Service's private key. It remains secret and is used for TLS authentication.
4. Generate Auth Service CSR
openssl req -new -key server.key -out server.csr -subj "/CN=auth-service"


Explanation:
- req – Handles certificate requests.
- -new – Creates a new CSR.
- -key server.key – Uses the Auth Service's private key to generate the request.
- -out server.csr – Saves the certificate signing request.
- -subj "/CN=auth-service" – Sets the Common Name to auth-service.
Purpose: Creates a CSR containing the Auth Service's public key and requested identity. It is used to request a CA-signed certificate. The private key is not included.
5. Create certificate extensions file
Create server.ext inside the auth-service folder.
subjectAltName = DNS:auth-service
extendedKeyUsage = serverAuth
keyUsage = digitalSignature, keyEncipherment


Explanation:
- subjectAltName – Specifies the Auth Service DNS identity.
- extendedKeyUsage – Specifies that the certificate is intended for server authentication.
- keyUsage – Specifies permitted cryptographic operations.
Purpose: Defines additional identity and usage information to include in the signed certificate.
6. Sign the Auth Service CSR using the CA
openssl x509 -req -in server.csr -CA ../ca/ca.crt -CAkey ../ca/ca.key -CAcreateserial -out server.crt -days 365 -sha256 -extfile server.ext


Explanation:
- x509 – Works with X.509 certificates.
- -req – Uses a CSR as input.
- -in server.csr – Reads the Auth Service CSR.
- -CA ../ca/ca.crt – Specifies the CA certificate.
- -CAkey ../ca/ca.key – Uses the CA private key to sign the certificate.
- -CAcreateserial – Creates a serial-number file if one doesn't exist.
- -out server.crt – Saves the signed certificate.
- -days 365 – Sets certificate validity to 365 days.
- -sha256 – Uses SHA-256 for the signature.
- -extfile server.ext – Includes the specified certificate extensions.
Purpose: The CA signs the Auth Service CSR and issues its certificate (server.crt).

Note: In this mock setup, we manually run the signing command. We haven't implemented a CA submission process or an authorization/allowlist check.

overall explanation (gpt)
A Certificate Authority (CA) is a trusted authority that issues digital certificates to individual microservices.

1. The CA generates its own private key (ca.key) and self-signed certificate (ca.crt).

2. Each microservice generates its own private key (server.key).

3. Using that private key, each service generates a Certificate Signing Request (CSR). The CSR contains the service's public key and requested identity.

4. The service submits its CSR to the CA.

5. The CA:
- Verifies whether the CSR is cryptographically valid.
- Checks whether the requesting service is authorized to receive a certificate.
- In our mock setup, we skipped the authorization check and manually signed the CSR.
6. If approved, the CA uses its private key (ca.key) to sign the certificate containing the service's public key and identity.

7. Each service receives its own signed certificate (server.crt).

8. During mTLS communication, services verify each other's certificates using the trusted CA certificate (ca.crt).
What does a certificate contain?
A certificate typically contains:
- Subject – Identity of the certificate owner.
- Public key – Public key belonging to the service.
- Issuer – CA that issued the certificate.
- Serial number – Unique identifier assigned by the CA.
- Validity period – Not Before and Not After dates.
- SAN – Subject Alternative Name, such as DNS:auth-service.
- Key Usage – Permitted cryptographic operations.
- Extended Key Usage – Intended purpose, such as server or client authentication.
- CA digital signature – Proves that the trusted CA signed the certificate contents.
